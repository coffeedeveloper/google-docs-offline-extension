# Google Docs 离线研究：下一步与设计缺口

整理日期：2026-09-24。目标是为自研文档系统提炼可靠的离线设计，不是完整复制 Google 的私有实现。

进展更新：已依据用户提供的真实 frame HTML 完成 [scheduler frame 主实现分析](SCHEDULER-FRAME.md)，确认消息分发、任务选择、执行环境和任务统计。P0 的具体文档处理、服务端确认与故障恢复实验仍未完成。

## 1. 当前证据到哪里了

已分析扩展的 offscreen 调度、iframe 创建和消息转发，以及网页 SW 的入口路由、资源准备、缓存版本和部分本地文档启动。网页代码还显示快照、命令、待处理队列与锁等存储结构。

但“一次编辑 → 本地可靠保存 → 后台执行 → 服务端确认 → 本地清理”的 Google 实际链路尚未闭合。[SW 调查](GOOGLE-SERVICE-WORKERS.md) 是特定版本静态分析；[Demo](../demo/README.md) 的 Yjs 和测试不是 Google 私有协议的证据。

下一步应沿文档生命周期调查，不必继续无差别还原全部 bundle。

## 2. P0：优先回答的四组问题

### 2.1 单篇文档什么时候才算可离线使用？

- 点击「可离线使用」后，谁发起准备：页面、隐藏 iframe，还是 worker？
- 下载完整快照、增量命令还是两者？图片、字体、评论与嵌入内容如何准备？
- 哪些数据和资源写入后才能显示就绪？中途断网如何恢复？
- 自动保留近期文档与用户显式固定，是否有不同的优先级与淘汰规则？

方法：专用文档启用前后，对比资源请求、数据库元信息、缓存和 UI 状态；不读取或归档其他真实文档内容。

产出：准备流程和就绪状态机。必须区分 SW 已激活、应用资源完整、目标文档完整。

Google 官方区分近期文件自动保存、手动指定离线文件及单篇就绪检查，但未公开其底层完成条件。[官方说明](https://support.google.com/docs/answer/6388102?hl=en)。

### 2.2 一次编辑如何可靠地保存到本地？

- 内存模型、快照、命令队列的写入顺序与事务边界是什么？
- 哪个提交点允许显示「已保存到设备」？写入失败如何呈现和重试？
- 重新启动时读快照还是重放日志？如何回收已经合并的命令？
- 配额不足、页面退出、进程终止时，已承诺保存的数据是否仍能恢复？

方法：离线输入唯一测试标记，等待本地保存提示，关闭并重启浏览器，仍然离线打开并验证；先保证专用测试数据和可恢复环境。

产出：保存事务、恢复算法与错误状态。当前页面断网后还能输入不等于具备可靠离线编辑。

### 2.3 谁执行同步，怎样判定成功？

优先追踪 `/offline/extension/frame`、`/offline/taskiframe`、`/offline/synctaskworker.js`、`/offline/eventbusworker.js` 的实际引用关系和实现，不能仅凭名称分配职责。

- 扩展指令最终在哪里执行？页面与后台同时存在时谁负责？
- 怎样选择待处理文档，控制并发、重试和退避？执行者退出后谁接手？
- 服务器已经接收但响应丢失时，如何避免重复生效？
- 响应返回期间又产生了新修改，确认事务怎样保护这些修改？
- 哪个确认点允许显示「已同步」？

产出：调度、上传、ACK 和本地提交的完整时序，以及任务所有权、幂等和失败恢复约束。发送成功、服务端接收、本地确认、UI 已同步不是同一时刻。

### 2.4 长时间离线后怎样接回远端版本？

方法：A 离线修改，B 在线修改相同位置，再让 A 恢复网络；进一步覆盖远端删除段落、删除文档、撤权、长时间离线与 `modelNeedsResync`。

需要回答：服务器历史不足时怎样恢复？重新获取快照会不会丢弃待上传修改？格式、评论与图片是否与正文采用一致的冲突策略？

产出：现有协同协议的离线兼容边界、重放与重建条件、不可自动合并时的恢复方式。无需凭客户端片段强行判定 Google 当前所有 OT/CRDT 细节。

## 3. P1：必须进入产品设计的风险

| 方向 | 待回答的问题 | 设计输出 |
| --- | --- | --- |
| 冷启动依赖 | HTML 是否依赖在线配置、登录跳转、动态 chunk、CDN？实际 scope/controller 是什么？ | 可复现启动路径和资源清单 |
| 升级兼容 | 新 SW、旧页面、旧模型能否共存？半成品更新怎样回退？ | 兼容窗口、迁移和回滚 |
| 多上下文并发 | 多编辑页、iframe、worker 如何避免重复处理和互相覆盖？ | 锁、所有权、接管机制 |
| 身份和权限 | 登录失效、登出、账号切换、撤权、企业禁用时怎样处理本地数据？ | 隔离、授权与数据处置规则 |
| 容量与回收 | 如何选择自动缓存范围？何时回收？是否保护未确认修改？ | 配额管理、保留策略和恢复提示 |
| 功能边界 | 创建、评论、建议、图片、附件、搜索、重命名哪些可离线？ | 功能矩阵与降级体验 |
| 运维与诊断 | 怎样区分资源未就绪、模型损坏、身份失效、同步失败？ | 隐私安全的状态与错误码、恢复入口 |

Google 官方规定一个浏览器 profile 只为一个账号开启离线；多租户、多账号产品不能假定直接继承该设计。[账号规则](https://support.google.com/docs/answer/6388102?hl=en)。

同源 iframe 与顶层页面的数据共享还应验证存储分区、扩展 host permissions 和 Cookie；不要把理论同源关系当作全部运行证据。[Chrome 文档](https://developer.chrome.com/docs/extensions/develop/concepts/storage-and-cookies)。

IndexedDB 写入不等于永久保留。需要研究 `navigator.storage.persist()` 的结果、配额失败和用户主动删除站点数据的边界。[持久化存储说明](https://web.dev/articles/persistent-storage)。

## 4. 建议实验顺序与证据标准

1. 建立官方原版基线：专用账号、文档与 profile，记录浏览器/扩展/脚本版本和实际 SW 注册。不要让替换扩展的兼容性问题污染对原始行为的观察。
2. 追踪「可离线使用」：得到资源和文档数据的准备链路。
3. 追踪「一次离线修改到确认」：得到保存、任务执行、上传和 ACK 时序。
4. 故障注入：浏览器重启、上传响应丢失、并发编辑、登录失效、更新中断。先限定测试对象和恢复方式。
5. 在 Demo 中验证提炼出的设计约束，不把 Google 的短符号、私有接口与部署结构当作自研必须照搬的部分。

每个结论分别标注源码证据、运行观察、架构推断或设计建议；保留版本、来源与失败样本。不把 Cookie、令牌、账号私密信息或真实文档内容写进仓库。

本清单是待办与方法，不代表实验已经完成。新增 frame 专题将单独记录本轮能够确认的部分。
